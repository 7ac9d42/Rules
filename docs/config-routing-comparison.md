# 正式原配置与新候选的分流差异

日期：2026-09-11。本报告记录[正式原配置](../configfull_new.yaml)与修补前候选的对比，历史候选SHA256及证据保留在文末；下文行号均指该快照；说明中的机场称呼统一为当前规范，历史报告与原配置保留当时名称。

后续处理：当前[候选](../configfull_new.yaml)已完成Docker精确规则、纯下载独立、隐私拦截代理放行和GLOBAL地区自动修补，并按后续用户用途及官方资料重新聚合为30个业务/工具入口，后续又新增Cloudflare Tunnel传输入口，后又恢复自建/家宽共享手选入口，当前共32个。AI与Tunnel随后补齐机场自动、地区、共享家宽和实际节点手选，默认策略保留。当前Docker归开发下载，严格媒体仍独立，普通影音与通信按类别聚合，TVB/Reddit独立；默认层级复评后Microsoft与境外通信采用成本，Google保留普通；单机场＋单地区自动继续不提供。随后三机场和四机场模板已拆为独立文件，层级自动别名由实际机场偏好吸收，地区选项改为机场优先名称。最新映射、依据与验收见[设计说明](single-config-design.md)、[分组依据](business-grouping-rationale.md)和[验收记录](config-optimization-audit.md)。下文“候选”与数字均指当时历史快照，正式配置及设备未切换。

结论：发现一条业务规则遗漏，以及一项先前要求保留但实际被合并的操作入口。另有三项链路选择能力收缩和PayPal默认地区变化，需要与普通业务合并区别看待。

## 1. 应补回的两项

### Docker R2下载主机脱离开发下载

原配置528行明确将以下主机交给Docker；候选Docker规则段545–555行删除了该精确条件，当前开发规则集合也没有覆盖它：

```text
docker-images-prod.6aa30f8b08e16409b46e0173d6de2f56.r2.cloudflarestorage.com
```

原生内核复现结果：

| 操作／请求 | 原配置 | 当前候选 | 临时补回精确规则 |
|---|---|---|---|
| 默认访问该R2主机 | Docker→通用机场名称3优先 | 通用代理→CF机场名称3优先 | 开发下载→CF机场名称3优先 |
| 开发类与通用组分别手选不同出口 | 受Docker选择控制 | 受通用代理选择控制 | 受开发下载选择控制 |
| `registry-1.docker.io` | Docker | 开发下载 | 开发下载 |

问题是一次Docker拉取的请求控制权被拆开；并非缺少代理兜底。CF只决定链路内部的探针，不应决定业务归属。Docker官方文档维护记录曾明确确认这个具体主机，因此不能只因它带Cloudflare后缀就删去Docker归属。[官方维护记录](https://github.com/docker/docs/issues/21960)

建议在`production.cloudfront.docker.com`之后补回一条精确DOMAIN规则，目标为开发下载。不要扩大匹配整个`r2.cloudflarestorage.com`。现有`scripts/test-real-rule-routing.py`曾把此主机期望写成通用代理；修补时必须一并纠正，否则测试只是在固化遗漏。

### 纯下载独立手选入口丢失

原配置445、454行提供纯下载select；候选469行将两个下载域和GitHub网页、API一并交给开发下载。专用测速算法仍存在，但用户不能再让大文件与GitHub交互业务分别手选出口。

先前“合并等价业务入口，保留特殊入口”的选择明确包含纯下载。保留内部算法不等于保留特殊入口，这项应认定为设计要求没有完整保留，不能仅用KISS解释。

最小补法是增加一个复用`Cost_policy`的纯下载select，让`pure_download_domain`指向它。四层政策、CF/GH子规则和所有现有测速池都可复用，不需要恢复旧的整套下载菜单。当前92组变93组、可见入口13变14；这是一个独立用途带来的一个独立选择状态。

对比阶段的临时补丁已验证：开发下载手选后，GitHub网页和Docker请求受其控制，两个纯下载域继续使用纯下载自己的默认链；所有业务入口手选标签时，两个下载域均归纯下载。后续已按用户意见落实到候选并更新验收脚本，最新结果见文首链接。

## 2. 真实的能力收缩，不能称为等价整理

| 能力 | 原配置 | 新候选 | 分析 |
|---|---|---|---|
| 单机场＋单地区自动 | 日本组内可选机场名称1日本url-test池 | 日本选项按层级跨机场；或直接选具体节点 | 无法再“只用机场名称1日本，但允许日本节点自动切换”。具体节点手选不等价；按YAGNI暂不扩展全部组合 |
| GLOBAL地区自动 | GLOBAL可选日本、台湾等地区组 | 只提供机场名称1优先／机场名称3优先、DIRECT和节点 | 地区自动能力被删。rematch不适用全局模式，并不妨碍引用已有可拨号地区fallback；若恢复，只需复用现有组 |
| 拦截误杀后经代理放行 | 隐私拦截可选节点选择 | 只剩REJECT、REJECT-DROP、DIRECT | 海外误杀服务可能直连仍不可用；恢复一个代理放行选项即可，不需要新增测速池 |

这三项与合并Google、GitHub等业务入口不是同一件事。对比时建议优先补回代理放行，GLOBAL地区自动按实际使用保留，单机场单地区自动不扩成组合矩阵；后续已落实前两项，用户已确认单机场单地区自动继续不提供。

PayPal是另一类变化：原配置默认“日本节点”，候选金融默认高要求链，当前可能从机场名称1日本变为机场名称1香港。它属于此前已说明的默认行为调整，不是漏规则，但确实影响地区稳定。采用候选时，需要日本偏好的金融业务应选“日本·高要求”。

## 3. 条件与优先级完整性

| 对比项 | 结果 |
|---|---|
| 主规则 | 127条→126条；条数变化不能证明功能减少或完整 |
| 原90个规则provider | 定义全部保留；新增CF补充名单和纯下载两个inline集合 |
| 明确DIRECT规则 | 40条内容及彼此相对顺序完全一致 |
| 两条纯下载精确域 | 改为同内容inline集合，域名条件等价，业务独立性见上文 |
| Docker R2精确域 | 被删除，未由开发集合补上；确定遗漏 |
| 两条Copilot精确域 | 新增`origin-tracker.githubusercontent.com`及`copilotprodattachments.blob.core.windows.net`→AI，属于已有设计中的最高层补齐 |
| 原主规则末位CF集合 | 移入自动子规则，CF识别不再改变业务归属 |
| 15个开发／HF／Docker／Kryptex／Linux DO条件 | 从顶部下移至广告、明确直连及Apple/B站规则之后，仍在`proxy_domain`与`cn_domain`之前 |
| 其他媒体、游戏、社媒和金融条件 | 按新业务入口归并，条件及原相对顺序保留 |

国内银行、`ifast_domain`、Steam CDN、网易云、私网、`trycloudflare.com`、Cloudflare国内域及人工直连主机均未漏掉。不能因为金融合并而把原本明确直连的国内银行、iFAST强制拉入金融代理组。

重排确实可能改变交叠条件的胜出者。原生测试把`huggingface.co`的匹配IP设为人工直连的`189.24.106.132`：原配置先中顶部HuggingFace规则，候选先中显式IP DIRECT。这符合明确直连优先的目标。另将`dl.google.com`设为普通CN-IP，原／新仍都命中开发规则；本次没有把末位CN-IP兜底移到所有已分类业务之前。

地区候选也有意收紧：原地区自动链最终可进入机场名称4的全地区池，候选机场名称4备用只留所选地区。全部台湾候选不可用时，候选可能拒绝，原配置可能跨区；这符合地区隔离目标，不应作为遗漏恢复。

机场名称4普通、CF和GitHub备用从跨区测速改为地区有序fallback；纯下载仍保留机场名称4全部候选测速。规则更新改用GitHub探针，3→1→4→DIRECT顺序保持。负载均衡、共享地区选择状态和基于节点名字猜测家宽的入口删除属于既定清理。

## 4. 默认路径的量化结果

域名见证从原／新两份规则共同生成，包含公开provider与两份主规则全部显式DOMAIN/DOMAIN-SUFFIX主机。只从候选provider生成见证会漏掉恰好被删掉的自定义Docker主机。

共18,076个静态域名见证。按新设计声明的业务归属映射后，只有3个归属差异：两个Copilot例外及Docker R2遗漏。这个映射用于比较规则条件，不意味着纯下载合并符合先前保留特殊入口的要求。

| 默认终结路径变化 | 见证数 | 含义 |
|---|---:|---|
| PayPal日本链→高要求机场名称1优先 | 245 | 地区默认变化 |
| 通用探针→GitHub探针 | 24 | 23个成本域、1个普通影音域，机场顺序仍属原层 |
| 通用探针→CF探针 | 12 | 10个成本域、2个普通／高要求域；包括上述Docker遗漏域 |
| 开发／GitHub→AI日本手选池 | 2 | Copilot精确例外 |
| 合计 | 283 | 不是283个错误，更不是283个独立服务 |

3,201个原DIRECT见证全部保持DIRECT，也没有新转DIRECT的纯域名见证。此结论不执行IP条件；前述显式IP交叠差异由原生测试另行覆盖。

旧配置已有的分类限制也应分开看：例如`fcm.googleapis.com`仍由Google／日常服务接管，`mtalk.google.com`仍由FCM／通用代理接管；`openaiassets.blob.core.windows.net`仍在开发下载。它们不是本次丢规则造成的新回归，不能仅凭名字在这轮强行改层。
