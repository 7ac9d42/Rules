# 服务探测与下载策略验证

验证日期：2026-09-09；候选过滤复核及厂商轻量探针实施：2026-09-10；首次连接计时及手选持久化复核：2026-09-11。运行测试使用官方 Mihomo v1.19.30；WRT 当时使用 `alpha-ge183c58`。本次只修改仓库中的配置模板，没有替换、重载或切换 WRT 的运行配置。后文标为历史的测试保留当时配置与结论，不代表当前探测地址。

## 配置行为

`release-assets.githubusercontent.com` 与 `codeload.github.com` 两个精确域共用 `纯下载`，在机场内的港日新美候选中执行 `url-test`，机场间使用 3→1→4 的 `fallback`；机场4保持原有全量末位备用。四机场恢复模板对应 3→1→2→4。GitHub 与 Cloudflare 各有使用自身探针的地区／机场链，保持机场3日本→新加坡→香港→美国、机场1香港→日本→新加坡→美国的原有顺序。

下载候选随订阅更新，但保留已有故障证据支持的排除：机场1的 HongKong 02–05、机场3日新的纯 CTCU 不进入对应自动下载池。倍率边界沿用原版：机场1/2全部地区及机场3港日新排除 ≤0.3x，机场3美国保留原有低倍率例外；下载池另排除 ≥5x、BETA、MITM 等成本或特殊用途标签。全量手动入口仍可选择。当前89个真实节点名称经本机核心核验：机场3有45个、机场1有15个、机场4有2个自动候选，手动入口有89个。数量随订阅变化，不是新增的每日优选名单。

共享地区与机场组保留原有质量排除、地区顺序和倍率过滤；GitHub 与 Cloudflare 的专属地区组沿用相同的节点筛选。只有两个精确下载域跨四地区择优。新增 Cloudflare 域名集合在既有业务规则、人工直连例外和国内IP安全网之后匹配，其余流量仍按原规则处理；不会因为网站使用Cloudflare托管就覆盖它已有的产品策略。DNS、TUN、订阅定义未变；9月11日关闭统一延迟，改用首次 HEAD 的建连及响应耗时。

当前按厂商归属使用以下三类轻量探针。GitHub 与 Cloudflare 的专属叶组、地区回退、机场回退使用同一厂商URL；Google服务直接复用已使用Google探针的原有共享链。可见选择组和下载手动入口显式提供对应 `testUrl`。这里的目标是避免某一厂商的探测劣化驱动另一厂商的默认选路，不把探针解释成文件吞吐或应用解锁状态。

| 服务入口 | 探测URL | 预期状态 | 能证明的范围 |
|---|---|---:|---|
| Google、GoogleVPN、YouTube、FCM | `https://www.gstatic.com/generate_204` | 204 | Google网络的轻量连接探测 |
| Cloudflare集合中未被前置规则接管的域名 | `https://cp.cloudflare.com/generate_204` | 204 | Cloudflare网络的轻量连接探测 |
| GitHub与纯下载（Release、源码归档） | `https://codeload.github.com/_ping` | 200 | GitHub旗下codeload连接探针；不等同于所有GitHub入口 |

GitHub 官方 runner 的连接诊断文档给出 `codeload.github.com/_ping`。本轮HEAD确认其返回200；`github.com/generate_204` 实际返回404，`github.com/_ping` 返回404，`github.com/_alive` 跳转登录，均未采用，也没有把GitHub探针的预期状态伪写成204。[GitHub官方连接诊断](https://github.com/actions/runner/blob/main/docs/checks/actions.md)

基础provider仍用gstatic，每60秒、3500毫秒检查；已有provider也决定额外厂商探测的周期和超时。GitHub与Cloudflare默认机场回退每45秒检查，纯下载每60秒检查。GitHub网页与下载共用一份按URL记录的节点健康状态，但分别按原地区顺序与下载跨区候选选路。删除重复的“源码归档”探测链后，provider只需Google、GitHub、Cloudflare三个URL任务，不再检查robots、CDN根路径404或固定版本归档。当前 `unified-delay: false`，单次成功 URLTest 只执行一次 HEAD；没有减少节点覆盖、探测频率或超时预算，也未测量实际计费流量或手机耗电。

GitHub／Cloudflare手动选择原有通用地区组时，仍采用那个组的原有策略；默认两条机场链已完整使用对应厂商探针。其他服务仍沿用原有策略，没有将所有第三方应用强行归入这三个厂商。

最终三个公开端点各进行了两轮 HTTP/1.1 HEAD（单次5秒上限、不跟随跳转），六次均返回对应的204／204／200。随后用临时 v1.19.30 核心通过本机当前网络再做六次原生3500毫秒测速，逐项检查 `extra[URL].alive` 及对应记录，全部通过；这验证目标与原生HEAD兼容，不是机场全节点性能测试。没有读取节点凭据或修改WRT，临时核心及运行目录已清理。

## 首次连接计时

交互体验需要考虑建连等待。当前关闭 `unified-delay`，计时从代理拨号之前开始，覆盖首次 HEAD 的建连及响应耗时；开启时，第二次 HEAD 成功会重新计时，主要反映已建立连接上的请求响应。底层协议仍可能复用隧道，因此关闭后也不是每次都强制冷启动，更不是吞吐测试。[v1.19.30 探测实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/adapter/adapter.go#L197)

9月11日在同一官方核心上用回环 HTTPS 完成12次调用。模拟线路A的连接准备耗时250毫秒、每次响应10毫秒；B分别为20、80毫秒。相同节点各测两轮：

| 设置 | A测得延迟 | B测得延迟 | 按探针延迟排序 | 每次成功调用的HEAD数 |
|---|---:|---:|---|---:|
| `unified-delay: true` | 10、10毫秒 | 80、80毫秒 | A优先 | 2 |
| `unified-delay: false` | 264、263毫秒 | 103、103毫秒 | B优先 | 1 |

该对照证明两种计时口径会改变排序；本配置选择首次建连口径，以避免连接建立慢的节点仅凭后续响应快而占优，不宣称它对所有应用或协议都更准确。另有两组故障对照：第二次 HEAD 超过300毫秒预算时，开启统一延迟的API返回504但按URL健康状态仍为真，关闭后单次HEAD正常完成；返回503却要求204时，两种设置的按URL健康状态均为假，但API仍可返回毫秒值。关闭统一延迟消除了第二次请求分支，没有修复状态码与API返回值的原生语义差异。

测试仅使用本机模拟代理和临时证书，证书只由临时核心信任；未访问外网、修改系统信任或连接WRT，运行目录及进程均已清理。三种厂商目标、机场顺序、质量筛选、50毫秒容差和探测周期保持不变。

## AI 固定机场一手选

AI 默认路径为 `AI(select) → AI-机场1-日本(select) → 机场一日本具体节点`，两层均为手选，不经过 `fallback` 或 `url-test`。AI入口也直接列出机场一其他节点供手动选择；不提供其他机场、通用自动组或直连候选。默认日本池沿用机场一日本组的质量过滤，筛选为空时使用 `REJECT`。

当前节点探测失败或实际请求失败时保持原选择，由用户手动换节点。9月11日按用户选择启用全局 `profile.store-selected: true`，AI及其他选择组均保留手选，重启后恢复同名候选；AI外层和日本子组的选择分别保存。没有缓存时仍使用配置默认值；已有同名缓存优先于YAML首项，修改默认顺序不会强制覆盖手选。运行目录需可写且在重启后保留。[官方配置说明](https://wiki.metacubex.one/config/general/#缓存)

原生持久化按组名和候选名匹配，不识别“同一节点换了名字”。订阅删除或重命名当前节点后，`select` 会退回该组首个候选，即使它探测不健康；AI仍只在机场一范围内，日本筛选为空仍拒绝。本机测试覆盖了正常重启保留两层选择及订阅改名失去选择的边界，没有进行AI平台实际解锁测试。[v1.19.30 选择实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/adapter/outboundgroup/selector.go#L96)

上一轮曾保留两类周期探测；下面是当时的评估，GitHub与codeload现已按本轮要求实施专属链：

- 通用连通性继续用 `https://www.gstatic.com/generate_204`，便于复用健康结果，开销低。
- 纯下载叶组与机场备用组统一用 `https://release-assets.githubusercontent.com/`，404只代表这一CDN入口。它不能证明codeload健康；本轮已出现两者不一致，归档失败仍要单独诊断。因此本轮已将codeload独立，不再借用Release探测结果。
- `https://github.com/robots.txt` 的200响应可以反映GitHub Web入口，已测出与通用目标不同的耗时；它不代表API限流、Git对象传输或下载带宽。要据此自动挑选叶节点，需要独立的地区选路链，并保持现有地区顺序；仅给顶层组改URL不能替换下层按gstatic选择的结果。本轮按服务反馈准确性的要求增加了独立链，仍未据此固定节点排名。
- Telegram图片使用MTProto及媒体数据中心路径；`telegram.org` 或 `web.telegram.org` 的HEAD不能代替图片传输测试，因此没有用它们作为图片体验指标。

## 普通 URL 与核心语义复核

HTTP 204 的含义是请求成功且无响应正文，并不自动赋予健康检查用途。HEAD 本身也不传响应正文；普通资源返回200在方法上可用于入口探测，但目标自身的缓存、应用处理、鉴权、限流及资源变动都可能影响结果。专用目标的优势应来自明确用途和稳定语义，不能只看状态码。[HTTP HEAD 与204规范](https://www.rfc-editor.org/rfc/rfc9110.html#name-head)

例如 GitHub 官方为 Copilot 网络排查给出的 `https://copilot-proxy.githubusercontent.com/_ping` 预期返回200；这是有文档支持的连接诊断目标，但不能外推为 GitHub 主站、Git 或 Release 的健康目标，官方 GET 示例也不能直接作为 HEAD 兼容性证明。本轮没有把它套用于现有三条链。[GitHub 官方网络排查文档](https://docs.github.com/en/copilot/how-tos/troubleshoot-copilot/troubleshoot-network-errors)

2026-09-10 对照实际本机核心的 **v1.19.30 标签源码**，用回环 HTTPS 服务分别关闭、开启 `unified-delay`，完成22次测速调用及两次正文断流请求。临时证书只由临时核心信任；未读取订阅或设备凭据，未连接 WRT。实验结果：

| 可控情形 | 实际反馈及边界 |
|---|---|
| 预期200，实际503 | 测速 API 仍返回毫秒值、全局 `alive=true`；`extra[该URL].alive=false` 且该URL延迟记录为0。不能只看面板数字或全局状态判定成功。 |
| 302跳转到另一条路径 | 没有访问跳转目标；预期200时该URL健康失败。 |
| HEAD 200，GET声明100字节却仅传5字节后断开 | HEAD健康成功；GET失败。HEAD无法证明正文完整。 |
| 第一次HEAD 200，第二次HEAD 503 | 开启统一延迟时，按第二次响应判为该URL失败。 |
| 第一次HEAD 200，第二次HEAD超过300ms实验时限 | 测速 API 返回504，但全局及该URL仍为健康，记录约301ms；第二次请求错误被忽略，保留第一次响应。这不是“两次均成功”。 |
| 同一URL先按预期200测503，再省略 `expected` 重测 | 该URL健康从失败变成成功；状态以URL为键，没有按预期状态另行隔离。手动测速条件可影响后续选路，直到后续检查更新。 |
| 首次响应人为延迟150ms，后续25ms | 关闭统一延迟记录约152ms，开启后约25ms；正常第二次请求计时不包含第一次完整连接过程，且仍包含服务端处理时间。 |

这些现象与 `URLTest`、测速接口及按URL读取状态的选路实现相符。原先关于 HEAD、不跟随跳转及分URL保存状态的判断成立；“状态不匹配就一定测速报错”“统一延迟要求两次成功”均不成立。此前实网 HEAD 样本与模拟故障注入只能证明采样响应及链路隔离，不能证明这三个普通URL已经成为可靠的业务健康指标。[v1.19.30 URLTest](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/adapter/adapter.go#L156)、[测速接口](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/hub/route/proxies.go#L98)、[按URL选择节点](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/adapter/outboundgroup/urltest.go#L96)

该轮只修正文档和配置注释，随后按用户明确的厂商归属需求替换为本文开头的轻量探针。原普通URL的限制与本节核心语义复核仍保留为历史证据；当前配置已撤下Release根路径404、robots和固定版本归档探测。

## 保留的边界

官方原版单配置没有持续带宽、历史成功率权重或连续多轮恢复确认。`url-test` 按近期延迟选择；`fallback` 会优先回选恢复的前项。机场3探测可用但吞吐较差时，不会仅凭下载速度自动让位给机场1。HEAD不读取文件主体，也不跟随跳转。[探测实现](https://github.com/MetaCubeX/mihomo/blob/e183c58/adapter/adapter.go)、[选择实现](https://github.com/MetaCubeX/mihomo/blob/e183c58/adapter/outboundgroup/urltest.go)

显式厂商 URL 可为 `use` 节点注册额外探测，但已启用的 provider 决定其周期与超时。同厂商不同业务共用一个探针只能反映所选入口，不能验证文件持续吞吐或应用解锁。[组解析](https://github.com/MetaCubeX/mihomo/blob/e183c58/adapter/outboundgroup/parser.go)、[provider检查](https://github.com/MetaCubeX/mihomo/blob/e183c58/adapter/provider/healthcheck.go)

控制器的 `testUrl` 为面板提供默认服务目标；面板若强制覆盖URL，或手动测速时自行传入其他 `expected` 状态条件，仍以该请求为准。本轮验证了内核定时探测及API字段，没有修改面板设置。`select`组API没有暴露 `expectedStatus`，不能宣称所有面板的手动测速都自动遵守配置状态码。[选择组API字段](https://github.com/MetaCubeX/mihomo/blob/e183c58/adapter/outboundgroup/selector.go)、[手动测速接口](https://github.com/MetaCubeX/mihomo/blob/e183c58/hub/route/groups.go)

`tolerance` 不是历史稳定性评分；已在当前版本复现与首成员位置有关的容差边界。本轮另测过用首位 REJECT 占位规避该边界，但它会改变全员探测失败时的尝试行为，可能拒绝实际仍能传输的路径，因此没有加入正式配置。

没有证据支持本轮调整 TUN MTU、协议栈或 DNS。先前针对三个 Telegram 地址的透明 TUN 握手均成功，官方公布网段也全部被现有集合覆盖；但小握手不能代表图片下载速度，不能宣称 Telegram 图片问题已经解决。
