# 香港、日本、新加坡地区顺序实测

日期：2026-09-11，WRT `172.16.199.1`，晚间窗口。目标：检验香港相对日本的延迟优势和波动；按追加要求加入新加坡，优势不大时再考虑调整地区顺序。

**实测阶段结论：仅按性能数据，加入新加坡后仍不调整默认顺序。** 机场名称1香港在当前配置的Google/CF计时下保持明显优势，新加坡没有提供更好的Google链路。香港对日本的复用连接优势只有约38–48ms，但首次建连差距更大；本轮也没有证实香港更不稳定。地区顺序、两份候选及生产配置均保持原值。

## 后续设计决策：机场名称1改为日本优先

用户随后将国际服务的地区适用范围纳入默认偏好，两份候选的机场名称1通用、GitHub、CF链统一改为**日本→香港→新加坡→美国**。这是权衡目标后的设计选择，不是对性能测试结论的改写；下文的“未调整”均记录实测阶段当时的决定。同期Google请求日本首次比香港慢287ms，复用慢38ms，仍接受这一代价。

地区限制确实有业务依据：例如[Google AI Studio与Gemini API官方地区列表](https://ai.google.dev/gemini-api/docs/available-regions)列出日本、新加坡，未列香港。但本配置AI已经独立采用日本，不能把这个例子算作普通Google业务此次新增的收益，也不能据此推断日本对所有国际服务都更兼容。节点IP信誉、账号地区与具体产品规则仍需分别判断。

探针成功只表示测试端点可达，不证明业务解锁、IP信誉或账号地区匹配。日本探针正常但某个服务拒绝访问时，自动链不会据此改选香港；有明确地区要求的业务仍应使用原有独立选择，无需增加一套地区策略。

只交换两份候选中各三条地区列表的前两项。机场间顺序、机场名称3及其他机场地区顺序、显式地区选择、AI手选和纯下载跨区测速保持既有设计；未部署到WRT。配置回归结果见[本轮验收](config-optimization-audit.md)。

## 1. 此前港日阶段：按实际候选范围测试

机场名称1的自动香港池排除 `HongKong 02–05`，低倍率/BETA也不进入该池；本轮覆盖实际合格的 HongKong 01，以及全部 Japan 01–05。机场名称3额外对照香港、日本各两个 VLESS 节点和一个 HY2 节点，均选用当前过滤条件允许的候选，不拿机场名称3已排除的日本 CTCU 节点代替正常池。

使用 WRT 同版本 Mihomo `alpha-ge183c58` 的独立临时实例，回环监听，GID 65534 按既有防火墙规则绕过生产透明接管。现有节点缓存只在路由器 `/tmp` 复制；不刷新订阅、不切换生产业务、不启用周期性健康检查。测试结束后临时进程、缓存与监听已清理。

比较三个现有探针：

| 家族 | URL | 预期状态 |
|---|---|---:|
| Google/通用 | `https://www.gstatic.com/generate_204` | 204 |
| Cloudflare | `https://cp.cloudflare.com/generate_204` | 204 |
| GitHub | `https://codeload.github.com/_ping` | 200 |

此前港日阶段共 **322 次检查/请求**，不含后续新加坡扩展：

1. 12 个节点、3 探针、3 轮，共 108 次统一延迟初筛，记录 `unified-delay: true` 的连接复用计时。
2. 两个机场各一对香港/日本节点，8 轮交替正反顺序；恢复与候选相同的 `unified-delay: false`，96 次原生测试，另加 64 次 Google 首次/复用连接请求。
3. 机场名称1全部6个合格港日节点，再按实际配置计时做3轮、3探针对照，共54次，避免只用一个日本节点推断整个地区。

八轮代表节点在初筛结束后固定为机场名称1 HK01 / JP02，以及机场名称3香港高速02 BGP CMCU / 日本高速01 BGP CUCM。原生测试超时3500ms；curl每次请求超时5秒，校验TLS证书。两种测速模式独立统计，不混合中位数；322是检查次数，统一延迟每次会发送两次HEAD，不等于实际网络HTTP请求总数。

## 2. 机场名称1结果

八轮固定节点对照，下面是成功样本的中位数；两边这些检查均成功：

| 测量项 | 香港01 | 日本02 | 差值 |
|---|---:|---:|---|
| 当前 Google 原生探针 | 430.5 ms | 611.5 ms | 香港快181 ms |
| 当前 CF 原生探针 | 435.5 ms | 684.0 ms | 香港快248.5 ms |
| 当前 GitHub 原生探针 | 699.0 ms | 734.5 ms | 香港快35.5 ms |
| curl Google 首次请求 | 481.0 ms | 609.0 ms | 香港快128 ms |
| curl Google 复用连接请求 | 115.1 ms | 162.9 ms | 香港快47.7 ms |

Google原生探针最大成功耗时：香港568ms、日本714ms；curl首次请求最大值：香港623ms、日本1088ms。复用请求均确认 `new_connections=0`。GitHub的香港最大值1230ms高于日本997ms，说明香港并非每个指标都更平稳。

再覆盖全部合格日本节点，三轮原生计时中位数如下；每格均3/3成功：

| 节点 | Google/ms | CF/ms | GitHub/ms |
|---|---:|---:|---:|
| 1-HK01 | 473 | 417 | 790 |
| 1-JP01 | 571 | 640 | 750 |
| 1-JP02 | 590 | 594 | 732 |
| 1-JP03 | 653 | 580 | 758 |
| 1-JP04 | 631 | 700 | 752 |
| 1-JP05 | 582 | 594 | 745 |

因此，当前Google计时下，香港相比各日本节点仍有约98–180ms的优势；CF优势约163–283ms。初筛稳态请求约40–50ms的差异，不能直接替代配置实际使用的探针延迟。

GitHub结果随轮次变化：八轮对照香港略快，后续全节点补测日本略快。这支持“GitHub港日差距较小”，但没有支持“日本在三种探针下统一更好”。本轮保持相同地区顺序，没有为短窗小差异拆出新的优先级例外。

仅此前港日阶段，机场名称1合计 **188次检查/请求全部成功**；这不包含随后新加坡节点的失败。它只能说明该窗口未发现失败率差异，不能证明两地长期可靠性相等，也不能证明香港没有高峰拥堵。

## 3. 机场名称3与稳定性边界

八轮代表节点对照中，日本的成功样本更快：Google中位数339ms，香港492ms；CF为361/483ms，GitHub为496/812ms。但日本代表节点分别只有5/8、7/8、7/8原生检查成功，香港三个探针均8/8。日本另外有一次curl首次请求超时。

这与“香港普遍更不稳定”不一致，也不能反向推广成“所有日本节点不稳定”：这里只复测一个代表节点，初筛还覆盖其他VLESS/HY2，地区池本来就允许换节点。没有用这批短窗超时新增节点黑名单或反转机场名称3已有的日本优先。

没有机场负载、在线人数或线路队列数据，不能把延迟/失败归因于香港用户更多。测试不是持续业务吞吐、全天丢包或长连接可用性评估；不把一次最大值称为有统计把握的业务p95。

## 4. 实测结束时的决策与配置状态

按事先采用的50ms参考值，机场名称1Google/CF的实际原生延迟优势仍明显超过该范围，且没有观察到香港更差的失败率，因此没有满足本次整体调序条件。50ms是沿用当前节点切换容差的工程参考，不是普适体验阈值。

当时两份候选保持：

- 机场名称1：香港→日本→新加坡→美国。
- 机场名称3：日本→新加坡→香港→美国。
- 未实测的机场名称2家宽模板及机场名称4后备顺序不外推调整。

所有业务选择、地区隔离、探针与回退参数保持；两份候选和正式配置哈希均与测试前一致，因此没有需要重新执行的配置路由回归。生产配置哈希和原进程身份保持，未部署或重启服务。

[原始数据、完整节点名称、脚本与摘要](/tmp/rules-hk-jp-qeqx1kyh/manifest.json)。curl失败时原始输出中的HTTP码为`000`，规范化统计仅将它转为数字0，并保留exitcode28与完整5秒失败耗时；失败没有从成功率分母删除。

## 5. 计时依据

Mihomo原生URLTest从拨号开始计时，并发送HEAD；启用统一延迟后再发送一次HEAD，第二次成功时改用第二次的耗时。当前候选为`unified-delay: false`。这解释了为什么复用连接的港日差距约48ms，而当前配置探针差距更大。[官方实现](https://github.com/MetaCubeX/mihomo/blob/Meta/adapter/adapter.go)、[URL-test容差](https://wiki.metacubex.one/config/proxy-groups/url-test/)
